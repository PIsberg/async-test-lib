# Guardrail generation

The `<project_guardrails>` blocks in `CLAUDE.md`, and every file under a module's `.claude/rules/`,
are generated by [vibetags](https://github.com/PIsberg/vibetags) from `@AI*` annotations in the
source. Nothing between the `VIBETAGS-START` / `VIBETAGS-END` markers survives the next compile.
This page covers the three configuration files that shape the output, and the one build workaround
the reactor needs. The operative rules are in the root [CLAUDE.md](../../CLAUDE.md#guardrails); this
is the reasoning behind them.

## The three config files at the reactor root

| File | What its presence switches on |
|------|-------------------------------|
| `.vibetags-root-index` | The root aggregate links to each module instead of embedding it |
| `.vibetags-roles` | Granular rules are grouped by role rather than one file per class |
| `.vibetags-cache` | Fingerprints of the watched inputs, so an unchanged round writes nothing |

### `.vibetags-root-index`

Without it the reactor root carries a byte-identical copy of every module's guardrails, so editing
a file inside `async-test-lib/` loads the same content twice: once from the root `CLAUDE.md` and
again from `async-test-lib/CLAUDE.md`. With it the root keeps each module's always-on safety tier
(`@AILocked`, `@AICore`, `@AIPrivacy`, `@AIIgnore`, `@AIAudit`, `@AISecure`) inline and replaces the
verbose per-element tier with a pointer to the module.

Keeping the safety tier inline is deliberate and was a bug fix in vibetags 1.0.0-RC8: before it, the
lean layout collapsed each module's region to a single pointer sentence, so a locked file's guardrail
only loaded once an agent opened the very file it was supposed to protect.

### `.vibetags-roles`

The library has around 130 annotated elements, most of them detectors under `diagnostics/`. One rule
file per class would mean ~130 files in `.claude/rules/` and a `<scoped_rules>` index in `CLAUDE.md`
listing every one. Roles collapse that to five groups that genuinely differ in how they must be
edited: `async-test-public-api`, `async-test-runtime-core`, `async-test-configuration`,
`async-test-detectors` and `async-test-instrumentation`.

First match wins, in file order. Anything ambiguous is pinned by fully-qualified name rather than by
a glob, because a same-named class in another package would match the same glob — both
`se.deversity.asynctest.DetectorRegistry` and `se.deversity.asynctest.spi.DetectorRegistry` match
`**/DetectorRegistry.java`, and they belong to different roles.

## Why Gradle needs `-Avibetags.root`

vibetags resolves a module's root by walking up from a source file to the nearest build file. Gradle
runs the compiler in a worker whose working directory is `~/.gradle/workers`, which is under neither
the module nor the reactor, so that walk lands nowhere. `build.gradle.kts` therefore sets

```kotlin
options.compilerArgs.add("-Avibetags.root=${project.projectDir}")
```

per module, putting Gradle's output where Maven's `ModuleRootResolver` already finds it.

This is still required as of vibetags 1.0.0-RC8. RC8 fixed Gradle *module identity* (it no longer
collapses every module onto a content hash), and it added a warning when a module cannot resolve its
root — removing the pin now produces `could not identify the compiling module … Pass
-Avibetags.module=<name> to name it, or -Avibetags.root so the module resolves under the root`, and
no guardrails are written. Verified by removing the line and running `./gradlew clean compileJava`.

## Both builds must agree

Maven and Gradle share one set of generated files, so whichever ran last wins. Before vibetags
1.0.0-RC8 the two emitted the same elements in different orders — javac's annotation-processing
round order is not constrained by the JLS — and running one after the other dirtied the working tree
with a diff that contained no actual change.

RC8 sorts by qualified name before emitting. Verified on this repo: `./gradlew build -x test` and
`mvn test-compile` now produce a byte-identical `async-test-lib/CLAUDE.md`, as do `mvn compile` and
`mvn test-compile`. A diff in a generated file is now a real change.

Because the two builds share this output, a version split between `pom.xml` and `build.gradle.kts`
makes the generated files depend on which build ran last. Keep `vibetags.version` and
`extra["vibetagsVersion"]` on the same number.
