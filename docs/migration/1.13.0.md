# Upgrading from 1.12 to 1.13.0

> See [INDEX.md](../INDEX.md) for the full documentation map, and
> [CHANGELOG.md](../CHANGELOG.md) (the 1.13.0 entry) for everything else it changes.

1.13.0 is a minor release that breaks the public API, by the owner's choice rather than a 2.0.0
([SUPPORT_POLICY.md](../SUPPORT_POLICY.md) records the exception). Five changes can affect a suite
that worked on 1.12. Three of them fail the compile, which is the easy kind. Two compile, pass and
quietly do something different, which is why this guide exists.

| Change | What you see after the bump | Issue |
|---|---|---|
| The 146 per-detector boolean attributes on `@AsyncTest` are removed | `cannot find symbol ... location: @interface AsyncTest` | #920 |
| The 42 `*Monitor()` accessors on `AsyncTestContext` are removed | `cannot find symbol` on the accessor | #921 |
| `spi.DetectorRegistry.build(config)` and the `spi.adapters` package are removed | `cannot find symbol` / `package does not exist` | #922 |
| A bare `@AsyncTest` runs `Preset.ESSENTIALS` (12 types), not all 146 | **Nothing.** The test compiles, passes and checks less | #923 |
| 21 of the detectors report findings under a different `Violation.detector()` name | **Nothing**, unless you filter structured findings by that string | #930 |

Every replacement for the first two rows, and the `detectAll = true` that keeps the old default,
already exists in 1.12.4 (checked against the published jar with `javap`), so that part of the
work can be done and verified green before the bump. The SPI replacements in
[the fourth section](#spidetectorregistrybuildconfig-and-spiadapters) are new in 1.13.0 and move
with the bump.

## First, decide which selection you want

Two of the five changes are about which detectors run, so settle that before rewriting anything.

**Option A: keep exactly what 1.12 ran.** Every `@AsyncTest` that does not say otherwise gets
`detectAll = true`. Nothing your suite checks shrinks, and the upgrade is mechanical. This is what
this repository did to 694 annotations in 95 files before flipping the default.

**Option B: adopt the new default.** `ESSENTIALS` is the default because most suites want the 12
high-signal detectors, none at the ADVISORY trust tier, without paying setup for all 146 on every
test. The way to get there without losing anything you rely on:

1. **Run everything once.** If your suite is green on 1.12 with the old default, this step is
   already done: 1.12 ran all 146 detectors on every bare `@AsyncTest`, and they found nothing.
   Otherwise, upgrade with Option A first and read the reports.
2. **Fix what they found** in the code under test, not in the test.
3. **Go back to the default**, keeping only what a test is actually about. A test that names a
   detector, because its subject is a `SecureRandom`, a cache or a `Semaphore`, keeps that
   detector in `includes`; everything else drops its selection attributes and runs `ESSENTIALS`.

The step that loses coverage silently is 3 done carelessly: a test that used to say
`detectSharedSecureRandom = true` and becomes a bare `@AsyncTest` no longer runs that detector,
because `SHARED_SECURE_RANDOM` is not in `ESSENTIALS`. The rewrite rules below keep it.

To run step 1 without editing annotations, pass `-Dasync-test.detectAll=true`
(`mvn test -Dasync-test.detectAll=true`, or `systemProperty("async-test.detectAll", "true")` on a
Gradle test task). It reads as `detectAll = true` on every `@AsyncTest` in the run; `includes` still
select exactly their list and `excludes` still apply. The same switch keeps `ESSENTIALS` on every
pull request and the full set on a nightly job. It arrives after 1.13.0 (#946).

## The boolean attributes on `@AsyncTest`

All 146 `detect*` / `validate*` / `monitor*` attributes were deprecated in 1.12 in favour of
`preset`, `includes` and `excludes`, and 1.13.0 removes them (#920). Each attribute's 1.12 javadoc
names its `DetectorType`; [DETECTOR_CATALOG.md](../DETECTOR_CATALOG.md) lists every detector and
what it reports.

**The obvious rewrite changes what runs.** Under 1.12's default, `detectAll = true`, a flag set to
`true` selected nothing extra: every detector was already on. So
`detectRaceConditions = true` rewritten as `includes = DetectorType.RACE_CONDITIONS` narrows the test
from 146 detectors to 1. That is usually what the author meant, and it is Option B; it is not what
the test did. What 1.12.4 actually ran, measured through `AsyncTestConfig.from` on the published
jar, and the 1.13.0 annotation that runs the same set:

| 1.12 annotation | 1.12.4 ran | Same set in 1.13.0 (Option A) | What the author probably meant (Option B) |
|---|---|---|---|
| `@AsyncTest` | 146 | `detectAll = true` | `@AsyncTest` (ESSENTIALS) |
| `detectX = true, detectY = true` | 146 | `detectAll = true` | `includes = { X, Y }` |
| `detectX = false` | 146 | `detectAll = true` | `detectAll = true, excludes = X` |
| `detectAll = false, detectX = true` | 144, all but `VISIBILITY` and `LIVELOCKS` | `detectAll = true, excludes = { VISIBILITY, LIVELOCKS }` | `includes = X` |
| `detectAll = false, detectVisibility = true, detectX = true` | 145, all but `LIVELOCKS` | `detectAll = true, excludes = LIVELOCKS` | `includes = { VISIBILITY, X }` |
| `detectAll = false` alone | 144, all but `VISIBILITY` and `LIVELOCKS` | `detectAll = true, excludes = { VISIBILITY, LIVELOCKS }` | `@AsyncTest` (ESSENTIALS) |

The `detectAll = false` rows are the trap: 144 of the 146 attributes defaulted to `true`, so
`detectAll = false` beside a few flags never meant "only these". In 1.13.0 `detectAll = false` only
declines the every-detector opt-in, so on its own it runs `ESSENTIALS`.

Do not write `excludes = { VISIBILITY, LIVELOCKS }` without `detectAll = true` to reproduce those
rows: `excludes` subtracts from the selection, and without `detectAll` the selection is
`ESSENTIALS`, so the result is 11 types, not 144 (measured on 1.13.0).

```java
// 1.12, deprecated: ran all 146 detectors
@AsyncTest(threads = 50, invocations = 100,
           validateLockOrder = true,
           detectFalseSharing = true,
           detectABAProblem = true)
void test() { }

// 1.13.0, Option A: still all 146
@AsyncTest(threads = 50, invocations = 100, detectAll = true)
void test() { }

// 1.13.0, Option B: the three the test is about
@AsyncTest(threads = 50, invocations = 100,
           includes = { DetectorType.LOCK_ORDER,
                        DetectorType.FALSE_SHARING,
                        DetectorType.ABA_PROBLEM })
void test() { }
```

`AsyncTestConfig`'s public boolean fields and the `Builder` setters such as
`detectRaceConditions(true)` are not removed (#383); only the annotation attributes are.

## The `*Monitor()` accessors on `AsyncTestContext`

All 42 were deprecated in favour of a `*Detector()` name, and 1.13.0 removes them (#921). For 38 of
them the suffix is the only difference:

```java
AsyncTestContext.lockLeakMonitor()   // 1.12, removed in 1.13.0
AsyncTestContext.lockLeakDetector()  // 1.12 and 1.13.0
```

Four do not follow that rule, because the new name says what the detector looks for rather than
what it wraps:

| 1.12 | 1.13.0 |
|---|---|
| `semaphoreMonitor()` | `semaphoreMisuseDetector()` |
| `completableFutureMonitor()` | `completableFutureExceptionDetector()` |
| `conditionMonitor()` | `conditionVariableDetector()` |
| `copyOnWriteMonitor()` | `copyOnWriteCollectionDetector()` |

And one name defeats a global search-and-replace of `Monitor` with `Detector`, which would rewrite
the first occurrence too:

```java
AsyncTestContext.nestedMonitorLockoutMonitor()   // 1.12
AsyncTestContext.nestedMonitorLockoutDetector()  // 1.13.0, not nestedDetectorLockoutDetector()
```

Anchor the replacement to the end of the identifier and all 42 are covered. The detector classes
themselves and their `record*` methods are unchanged: a public-API diff of 1.12.4 against 1.13.0
removes no member of any class in `diagnostics`.

## The default selection

A bare `@AsyncTest` ran every detector in 1.12; in 1.13.0 it runs `Preset.ESSENTIALS` (#923):
`DEADLOCKS`, `LIVELOCKS`, `RACE_CONDITIONS`, `ATOMICITY_VIOLATIONS`, `CONCURRENT_MODIFICATIONS`,
`LOCK_LEAKS`, `RESOURCE_LEAKS`, `THREAD_LEAKS`, `INTERRUPT_MISHANDLING`,
`COMPLETABLE_FUTURE_EXCEPTIONS`, `COMPLETABLE_FUTURE_COMPLETION_LEAKS` and
`UNCAUGHT_EXCEPTION_HANDLER`. The defaults behind it are `detectAll = false` and
`preset = Preset.ESSENTIALS`. How the attributes combine, measured on 1.13.0:

| Annotation | Runs |
|---|---|
| `@AsyncTest` or `detectAll = false` | `ESSENTIALS`, 12 |
| `detectAll = true` | all 146, whatever `preset` says |
| `preset = Preset.STRICT` (or `ALL`) | all 146 |
| `includes = X` | exactly `X`, even beside `detectAll = true` |
| `detectAll = true, excludes = X` | 145 |

This is the change a compiler cannot show you. Whether to keep the old selection or adopt the new
one is [the decision above](#first-decide-which-selection-you-want); either way, look at every
`@AsyncTest` that sets none of `includes`, `preset` or `detectAll`, including annotations on
classes and composed annotations.

```java
// 1.12: every detector.  1.13.0: Preset.ESSENTIALS
@AsyncTest(threads = 8)

// Every detector, in both
@AsyncTest(threads = 8, detectAll = true)
```

## `spi.DetectorRegistry.build(config)` and `spi.adapters`

The built-in SPI bridge is gone (#922): the `se.deversity.asynctest.spi.adapters` package and
`spi.DetectorRegistry.build(config)`, which returned a fresh, unobserving copy of every built-in
detector beside your own. Your own `DetectorFactory` keeps working through `buildExternal(config)`,
which the runner already used and which exists in 1.12. Code that called `build(config)` wanted one
of two things:

```java
// 1.12: which detectors does this config select?
DetectorRegistry.build(cfg).all()
// 1.13.0
cfg.enabledDetectors()                        // Set<DetectorType>; also cfg.isEnabled(type)

// 1.12: find my third-party detector
DetectorRegistry.build(cfg).get(MyDetector.class)
// 1.13.0
DetectorRegistry.buildExternal(cfg).get(MyDetector.class)   // or .get("com.acme.my-detector")
```

`Detector.type()`, `DetectorFactory.type()` and `DetectorFactory.isEnabledFor(config)` became
default methods, so an existing implementation still compiles. A third-party detector can now
return its own `id()` instead of borrowing a built-in `DetectorType` (#919); two detectors that
borrowed the same constant replaced each other in the registry, and still do until one of them
overrides `id()`.

## `Violation.detector()` names

21 of the detectors put a third spelling of their name into `Violation.detector()`, neither the class
name nor the alias the other 125 use, so `DetectorTrust` could not resolve their tier (#930). They
now use the alias. Listeners and `AsyncFindings` receive the class name and are not affected; code
that reads `report.structuredViolations` and matches on the old string is. So is SARIF:
`SarifFormatter` uses the same string as the rule `id` and `name`, so a code-scanning tool that
tracks alerts by rule sees these 21 rules as new, closing the old alerts and opening new ones on the
first 1.13.0 upload.

| Old | New |
|---|---|
| `BusyWait` | `BusyWaiting` |
| `CompletableFutureCommonPoolBlocking` | `CfCommonPoolBlocking` |
| `CompletableFutureCompletionLeak` | `CompletableFutureCompletionLeaks` |
| `CompletableFutureException` | `CompletableFutureExceptions` |
| `ConcurrentModification` | `ConcurrentModifications` |
| `ConditionVariable` | `ConditionVariables` |
| `CopyOnWriteCollection` | `CopyOnWriteCollections` |
| `HttpClientConcurrency` | `HttpClient` |
| `InheritableThreadLocalMisuse` | `InheritableThreadLocal` |
| `Livelock` | `Livelocks` |
| `LockLeak` | `LockLeaks` |
| `ParallelStream` | `ParallelStreams` |
| `ResourceLeak` | `ResourceLeaks` |
| `ScopedValueMisuse` | `ScopedValue` |
| `SemaphoreMisuse` | `Semaphore` |
| `SharedCollection` | `SharedCollections` |
| `StructuredConcurrencyMisuse` | `StructuredConcurrency` |
| `ThreadLeak` | `ThreadLeaks` |
| `VirtualThreadContextLeak` | `VirtualThreadContextLeaks` |
| `VirtualThreadCpuBoundTask` | `VirtualThreadCpuBound` |
| `Wakeup` | `WakeupIssues` |

## Checking your suite is ready

Compile on 1.12 with deprecation warnings visible. A build with none left survives the three
compile-breaking changes; the Maven flag turns javac to `[debug deprecation target 21]` and reports
every deprecated call site.

```bash
mvn -Dmaven.compiler.showDeprecation=true test
```

Gradle does not pass `-Xlint:deprecation` by default, and `--warning-mode all` reports Gradle's
own deprecations rather than javac's. Ask javac directly:

```kotlin
tasks.withType<JavaCompile>().configureEach {
    options.compilerArgs.add("-Xlint:deprecation")
}
```

Then the two silent changes: list every `@AsyncTest` that sets none of `includes`, `preset` or
`detectAll` and decide for each, and search for the old `Violation.detector()` names in the table
above.

After the bump, `AsyncTestConfig.from(annotation).enabledDetectors()` tells you exactly which
detectors an annotation selects; every count in this guide was measured that way (and, for 1.12.4,
by reading the public boolean fields of the same config).
